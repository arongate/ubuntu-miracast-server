# Miracast Sink P2P Implementation Reference

## Correct Architecture: Autonomous GO (NOT GO Negotiation)

The industry-standard approach for a Miracast sink is **Autonomous Group Owner** mode:
- Sink creates its own P2P Group Owner FIRST
- Source discovers the GO beacon via standard P2P scan  
- Source connects via WPS PIN exchange
- This avoids the fragile GO Negotiation timing issues

## Complete Working Flow (lazycast/7herbert proven approach)

```bash
# 1. Setup
wpa_cli -p <ctrl> -i <iface> set wifi_display 1
wpa_cli -p <ctrl> -i <iface> wfd_subelem_set 0 000600111C44012C
wpa_cli -p <ctrl> -i <iface> wfd_subelem_set 1 0006000000000000
wpa_cli -p <ctrl> -i <iface> wfd_subelem_set 6 000700000000000000
wpa_cli -p <ctrl> -i <iface> set device_name "My Sink"
wpa_cli -p <ctrl> -i <iface> set device_type 7-0050F204-1
wpa_cli -p <ctrl> -i <iface> set p2p_go_ht40 1
wpa_cli -p <ctrl> -i <iface> p2p_find type=progressive

# 2. Create autonomous P2P Group Owner
wpa_cli -p <ctrl> -i <iface> p2p_group_add persistent
# → Creates group interface (e.g., p2p-0)
# → Emits P2P-GROUP-STARTED <group_iface> GO

# 3. On the GROUP interface (not p2p-dev!):
wpa_cli -p <ctrl> -i <group_iface> wps_pin any <PIN>
# → Arms WPS registrar with PIN
# → Display PIN on screen for user

# 4. Wait for connection:
# Event on group interface: AP-STA-CONNECTED <mac>

# 5. After connection:
# - Run DHCP server (dnsmasq) on group_iface
# - Assign static IP (192.168.173.1/24) and run DHCP for clients
# - Wait for peer to get DHCP lease (poll dnsmasq leases / ARP table)
# - Connect TO source's RTSP server at <peer_ip>:7236 (sink is RTSP CLIENT)
# - Perform RTSP M1-M7 negotiation, then receive RTP stream on UDP port 1028
```

## Key Events to Monitor (on GROUP interface after p2p_group_add)

- `P2P-GROUP-STARTED <iface> GO` — Group created, get interface name
- `AP-STA-CONNECTED <mac>` — Source connected via WPS
- `AP-STA-DISCONNECTED <mac>` — Source disconnected
- `P2P-GROUP-REMOVED <iface>` — Group destroyed

## Key Differences from GO Negotiation Approach

| Aspect | GO Negotiation (broken) | Autonomous GO (correct) |
|--------|-------------------------|------------------------|
| Discovery | p2p_listen (fragile) | GO beacon (always visible) |
| PIN timing | Must respond to PROV-DISC in time | PIN pre-armed, user has unlimited time |
| WPS command target | p2p-dev interface | GROUP interface |
| Reliability | Many failure modes | Very reliable |
| Used by | (nobody successful) | lazycast, 7herbert, commercial sinks |

## WFD Subelement Details

- ID=0 (Device Info): `0006 0011 1C44 012C`
  - 0011 = Primary Sink (01) + Session Available (10)
  - 1C44 = Port 7236
  - 012C = 300 Mbps throughput
- ID=1 (Associated BSSID): `0006 000000000000` (none)
- ID=6 (Coupled Sink Status): `0007 00000000000000` (not coupled)

## Realtek rtw89 Driver Notes

- RTL8852CU (TP-Link AXE5400) uses rtw89_8852cu driver
- Confirmed working as P2P-GO by 7herbert project (RTL8852BU)
- P2P commands go through parent interface (no p2p-dev-* control socket)
- Supports concurrent managed + P2P-GO on different channels

## Critical Mistake in Previous Implementation

Used `p2p_listen` + `P2P-PROV-DISC-SHOW-PIN` + `p2p_connect ... display auth` (GO Negotiation path).
This fails because:
1. Timing issues (PROV-DISC can expire before response)
2. Source may not initiate GO Negotiation after PIN timeout
3. PIN is generated by wpa_supplicant, not controlled by app
4. Events lost due to wpa_cli buffering issues

Fix: Switch to Autonomous GO mode with `p2p_group_add` + `wps_pin any`.

## RTSP Direction (CRITICAL)

In Wi-Fi Display, the **Sink is the RTSP CLIENT** and the **Source is the RTSP SERVER**.
After P2P connection + DHCP, the SINK connects TO the SOURCE's port 7236.

```
Source (phone)                  Sink (us)
  RTSP server :7236  ←────────  RTSP client connects
  M1: OPTIONS →                  ← 200 OK
       ← M2: OPTIONS             → 200 OK
  M3: GET_PARAMETER →            ← 200 OK + capabilities
  M4: SET_PARAMETER →            ← 200 OK
  M5: SET_PARAMETER (trigger) → ← 200 OK
       ← M6: SETUP               → 200 OK + Session
       ← M7: PLAY                → 200 OK
  ──── RTP stream (UDP) ────→    receives on port 1028
```

DO NOT implement a listening RTSP server on the sink side. The sink CONNECTS to the source.

## Sources

### Protocol Specifications
- **Wi-Fi Display Technical Specification v2.1** — Wi-Fi Alliance, 2017. Defines WFD device types, subelements, RTSP/WFD message sequence (M1-M7), capability negotiation, and transport setup. Access requires Wi-Fi Alliance membership: https://www.wi-fi.org/discover-wi-fi/wi-fi-display
- **Wi-Fi Peer-to-Peer (P2P) Technical Specification v1.7** — Wi-Fi Alliance, 2016. Defines Group Owner Negotiation, Autonomous GO, Provision Discovery, WPS PIN/PBC methods, and P2P group formation: https://www.wi-fi.org/discover-wi-fi/wi-fi-direct
- **Wi-Fi Protected Setup (WPS) Specification v2.0.7** — Wi-Fi Alliance, 2016. Defines PIN and Push Button Configuration authentication flows.
- **IEEE 802.11 (Wi-Fi)** — underlying wireless standard for P2P operation channels and concurrent mode support.
- **IETF RFC 2326 (RTSP 1.0)** — Real Time Streaming Protocol used for Miracast session control (M1-M7 messages).
- **IETF RFC 3550 (RTP)** — Real-time Transport Protocol for media delivery over UDP.
- **ISO/IEC 13818-1 (MPEG-TS)** — Transport Stream container used to multiplex H.264 + AAC over RTP.
